# External MQTT recovery contract

`roomci external-mqtt` evaluates a separate gateway process using reports received through a real MQTT broker. This is a reference regression for the contract **latest desired state wins after reconnection**. It is not evidence of compatibility with a customer SUT.

## Run and observation boundary

Compose places the SUT on a private network with Toxiproxy and the broker on a separate network with Toxiproxy and roomci. Before checking the SUT's direct route, the run script confirms a broker MQTT CONNACK from the broker network; it checks readiness again afterward. Its negative controls reject both a stopped broker and an intentionally connected bypass route. Compose starts containers, while the CLI independently waits for its observer's initial MQTT connection and SUBACKs within `ready_timeout_ms`.

The runner and SUT share a fresh run ID and device ID in their MQTT topic prefix: `roomci/<run-id>/<device-id>/{desired,reported,status}`. The runner subscribes before sending a desired message. It ignores retained replay on `reported`, malformed payloads, and payloads whose run/device differ. It accepts a report only when the SUT publishes JSON containing the exact run ID, device ID, revision and value. The SUT sees MQTT messages and topic settings, not an expected verdict or fault phase. The runner label `--sut-version` is report metadata only.

The broker is Eclipse Mosquitto 2.0.22. The SUT connects only through Toxiproxy 2.12.0; the roomci publisher/observer connect directly to the broker. MQTT 3.1.1, QoS 1, and `clean_session=true` are intentional. Desired messages are retained so a re-subscribing SUT receives revision 2 after reconnect; QoS 1 PUBACK proves the broker accepted each desired message. The SUT publishes non-retained reports and an online status. Its non-retained offline last will provides evidence that the broker lost the existing SUT connection. With a clean session, the broken SUT's omission of the reconnect SUBSCRIBE reliably loses the desired update. The fixed SUT subscribes in every successful `on_connect`. The two modes use the same contract and verdict code.

## Sequence and verdict

1. Wait at most `ready_timeout_ms` for the observer's MQTT connection and both SUBACKs. Temporary network errors during this initial readiness stage are retried within that bound; a later observer connection error remains an inconclusive test failure. Publish revision 1; require the SUT's matching report within the same configured bound. Failure to establish these prerequisites is `inconclusive`.
2. Record `fault_requested`; disable the named Toxiproxy proxy; GET the disabled state; verify every resolved listener address refuses a new connection; observe the SUT offline will within one `fault_timeout_ms` deadline. These are separate `fault_applied` and `fault_affected_sut` evidence events. An unchecked address, failed operation, or missing effect is `inconclusive`.
3. Publish retained revision 2 through the direct broker connection and wait for QoS 1 PUBACK. Start the `recovery_timeout_ms` monotonic deadline before re-enabling the proxy. POST, GET, MQTT CONNACK probing across resolved addresses, retries, and SUT reconnection share that deadline. The observer continues processing broker reports while the probe waits. If the data path does not return by the deadline, the verdict is `inconclusive`.
4. Require a matching revision 2 report received by the observer before the deadline. A dedicated observer worker timestamps MQTT events with a monotonic clock as they are received, even while the main runner probes the proxy. A revision 2 report with the wrong value is `wrong_latest_value`; no matching report is `missing_latest_report`. After reaching the latest value, a different report received within `stability_ms` is `rollback_observed`. Before passing, the runner drains immediately available queued events and checks their receipt times; an undrainable queue is inconclusive, while post-window reports cannot reverse a stable verdict. A report or CONNACK completed after its deadline cannot establish success. The verdict is then frozen; later MQTT messages cannot change the report.
5. Attempt proxy cleanup even on error. A cleanup error makes the run inconclusive. JSON and JUnit are written for pass, SUT failure, and environment failure; exit codes are 0 for pass, 1 for a completed non-pass, and 2 for invalid contract or report I/O failure.

Timeline event timestamps are UTC wall-clock values for diagnostics; all waiting and deadlines use a monotonic clock. `verdict=failed` means prerequisites held but SUT behavior failed. `verdict=inconclusive` means a prerequisite, fault, observer, or cleanup failed. Both yield a failed JUnit assertion and nonzero CI status. A contract without its required latest value or stability window fails validation.

The JSON report contains the roomci version, SUT version label, run ID, strict contract, expected and observed values, operation/observation timeline, assertion, verdict, and reason. The report uses `evaluation_target=external_sut` and `observation_source=real_mqtt_broker`. Ordinary `roomci run` and `roomci serve` still evaluate the virtual-time internal model. The existing `/run` produces its internal verdict before any external overlay; `/fault` records a request but does not apply a network fault, and `/finish` closes that service session. None of those endpoints provide this external verdict. The limited embedded MQTT endpoint remains a separate PoC ingress, not the broker used here.

## Run and replace the reference SUT

From the repository root, run `bash examples/external-mqtt-recovery/run.sh`. Docker Compose builds the runner and SUT, starts Mosquitto and Toxiproxy, runs fixed and broken SUTs plus negative controls, validates exact JSON verdicts and reasons, writes JSON/JUnit/logs under `reports/external-mqtt`, then tears the stack down. The GitHub Actions `external-mqtt-recovery` job uses the same command and uploads those artifacts. The `broken` case must fail specifically with `missing_latest_report` after `initial_ready`, `fault_applied`, `fault_affected_sut`, and `fault_released`; an arbitrary nonzero exit does not satisfy the job. The retained negative control also requires an `ignored_retained_report` event containing the injected payload and no equivalent accepted `sut_reported` event.

To substitute a customer SUT in this Compose setup, start it on `sut_net` and configure its MQTT connection endpoint as `toxiproxy:1884`. The Toxiproxy **proxy name** used by its control API is `sut`; it is not the DNS hostname. Make the SUT use the run-specific topic prefix. Configure its normal desired and reported topic/payload mapping, initial and latest values, ready/fault/recovery/stability deadlines, and a reliable disconnect evidence source. The reference JSON `run_id`, `device_id`, `revision`, and `value` mapping is an adapter boundary: a customer with different correlation fields or a different report format needs a mapping adapter before this verdict can claim to test that SUT. A customer without an offline will needs another verifiable connection-loss signal. The minimal example has no MQTT authentication; customer use needs broker credentials/ACLs so an unrelated publisher cannot impersonate the SUT on its reported topic.

The external contract intentionally has no `faults[].duration`: it explicitly applies and releases one SUT-only TCP cut. Internal-model `faults[].duration` and step fault durations are rejected before execution until their recovery semantics exist. `mqtt.local.enabled: false`, `mqtt.*.retained: false`, and unknown structured `mqtt` keys are rejected; arbitrary MQTT payload maps remain open for adapter data.

The proxy's disable/enable API is documented by [Toxiproxy](https://github.com/Shopify/toxiproxy), and [Paho's reconnect guidance](https://github.com/eclipse-paho/paho.mqtt.python) explains why the fixed client subscribes in its connection callback.
